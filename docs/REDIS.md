# Redis behavior

Redis is an internal, password-protected, bounded cache and shared fixed-window admission counter. The API uses a single Lua increment/expiry command across replicas (300 requests/IP/60 seconds). IPs are SHA-256 digests in Redis keys. The API does not trust proxy headers by default; configure a trusted reverse-proxy deployment deliberately before enabling forwarded addresses.

If Redis is unavailable, API admission returns 503 promptly. This fails closed and preserves the shared quota. Jobs already committed to PostgreSQL continue running in C++. Cache operations independently bypass Redis failures. The client disables offline command buffering, bounds command count to 256, times commands out after 400 ms, and reconnects with capped backoff. Readiness checks PostgreSQL; `/api/v1/infrastructure` separately reports Redis readiness and process-local cache hit/miss/error counters. A Redis outage does not delete acknowledged jobs.

Job detail reads first query the project-owned PostgreSQL `state_version`. Redis keys include project, job, and version. The full job/attempt snapshot is read in one SQL statement on a miss. Every job or attempt change advances the version, including lease metadata, so a late cache writer cannot make old state current. Active entries expire after 5 seconds, terminal entries after 60 seconds. Wrong-project or corrupt entries are treated as misses. This still costs a small PostgreSQL read per hit; the benefit is avoiding the larger job/attempt snapshot and JSON assembly, not eliminating database dependency. Cache data includes job payload/result: keep Redis private and authenticated.

Run `node scripts/setup-env.mjs` to append a missing Redis credential without rotating existing database secrets. `docker compose up -d --build` provisions it internally without a host Redis port. The disposable public test stack uses no Redis password because it has no published ports or durable data. Run the suite documented in TESTING.md to verify exact concurrent quota across two API replicas, stale-version/foreign entries, TCP outage, fail-closed behavior and automatic reconnect. Measured cache results belong in the benchmark report; no speedup is assumed.
